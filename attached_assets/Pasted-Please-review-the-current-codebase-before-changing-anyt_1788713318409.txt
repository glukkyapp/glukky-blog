============================================================
PRODUCT RULES
============================================================

1. Every individual food component must have a stable internal ID.

Examples:

- 米線 / Rice noodles / mai sin → `maisin`
- 河粉 / Ho fun → `ho_fun`
- 腸粉 / Rice noodle rolls → `cheung_fun`
- Default milk tea / 奶茶 → `naai_cha_sweetened`
- Explicitly unsweetened milk tea / 無糖奶茶 / 走糖奶茶 → `naai_cha_unsweetened`

The internal ID is an app-owned canonical identifier. It may use a fixed Cantonese romanisation convention, but it is not a user-facing label and must remain stable over time.

2. English, Traditional Chinese, and Cantonese names are display/search labels only.

The app must continue storing and returning:

- `nameEn`
- `nameZhHant`
- `nameYue`

The UI must continue displaying the appropriate localized label according to the active app language.

3. Food identity must not depend on translated names.

The same food must remain one food even if the model later outputs different English wording, simplified-vs-traditional variants, spelling differences, punctuation differences, or another valid translation.

For example, all of these should resolve to the same component ID:

- Rice noodles
- Rice vermicelli
- 米線
- 米线
- mai sin
- maisin

They should not become separate frequency, HStix, pairing, or GI entities.

4. Milk tea default rule: unspecified sugar means sweetened.

Do NOT create an “unknown sugar” state that prevents GI resolution.

Required behaviour:

- `奶茶`, “milk tea”, or a milk tea with no sugar qualifier
  → `naai_cha_sweetened`
  → treated as a sweet drink
  → resolves to the sweetened milk tea GI reference

- `無糖奶茶`, `走糖`, “no sugar”, “sugar-free”, or “unsweetened”
  → `naai_cha_unsweetened`
  → not classified as a sweet drink under the existing explicit-no-sugar rule
  → use the appropriate unsweetened handling/mapping decided by the controlled vocabulary

============================================================
CHANGE 2 — DIRECT GI LOOKUP BY COMPONENT ID
============================================================

GI lookup must stop using translated-name concatenations as its primary identity.

The current GI identity appears to use multilingual name fields and fuzzy/alias/category matching. Replace the normal runtime path with:

```text
component internalId → controlled GI reference mapping → GI value/rank
```

Examples:

```text
maisin                   → noodles-rice GI reference
ho_fun                   → noodles-rice GI reference
cheung_fun               → noodles-rice GI reference
naai_cha_sweetened       → sweet-drink-milk-tea GI reference
```

Several canonical component IDs may intentionally map to the same GI reference. That is allowed and expected when the best available reference is shared.

Please inspect and report on the impact to:

- `giFoodKey()`
- `normalizeGiFoodIdentity()`
- `getGiCandidatesForFood()`
- `food_gi_entries.normalizedFoodName`
- GI cache uniqueness and existing cache entries
- GI resolution jobs/claims/statuses
- GI candidate tables
- any Claude-powered GI candidate-selection workflow
- `/api/snap/food-frequency` GI annotations
- GI display states: resolved, pending, unavailable

The intended end state is:

- Known controlled component ID with a mapped GI reference → resolve directly.
- Known controlled component ID with no supported GI reference → unavailable.
- Unknown/unmapped component → unavailable or pending only if there is an explicit curation workflow.
- Do not use broad substring matching or category-only matching to silently assign a GI value at runtime.
- Do not create an “unknown sugar” exception for unqualified milk tea; default it to sweetened.

Please advise whether the GI database column should be renamed later from `normalizedFoodName` to something clearer such as `componentInternalId` or `foodComponentId`, and whether that should be one migration or a backward-compatible staged migration.

============================================================
NON-GOALS / DO NOT BREAK
============================================================

Do not replace or reuse meal-combination identity as the component identity.

These are different concepts:

```text
foodLabels.internalId / mealSnaps.comboKey
= a full meal configuration, including meal name, portion, sauces, and toppings.

FoodItemMetadata.internalId
= one individual food component shared across meals.
```

For example:

```text
wonton_noodles__medium__chili_oil
```

is a meal-combination ID, while:

```text
wonton_noodles
egg_noodles
choi_sum
```

would be individual component IDs.

Keep the existing multilingual labels. Do not show internal IDs to users.

Do not silently merge historical records with an unsafe fuzzy match. If backfilling legacy records requires a matching strategy, propose it clearly and identify records that should remain unresolved rather than guessed.
