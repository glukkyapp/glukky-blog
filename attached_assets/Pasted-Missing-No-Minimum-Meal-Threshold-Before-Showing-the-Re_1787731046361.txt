Missing: No Minimum-Meal Threshold Before Showing the Reminder
The ticket title calls this "Recurring Food Frequency Insights," and the spirit of the feature (established earlier in this thread) was to wait until there's enough logged history — 25 meals — before surfacing any pattern. Nothing in "Done looks like" or "Steps" gates the reminder on a minimum count. Without it, a user with 3 logged meals could see "Milk tea appeared in 1 of your last 3 logged meals," which isn't a recurring pattern, it's a single data point dressed up as one. Add an explicit gate consistent with the previously agreed threshold.

Missing: Partial-Sugar Wording Isn't Handled, Only Full Exclusion
The no-sugar exclusion list (無糖, 走糖, 走甜, no sugar, unsweetened) only covers the binary case. It doesn't address common reduced-sugar orders — 少甜, 半糖, 微甜 (less sweet, half sugar, slightly sweet) — which are neither "no sugar" nor full-sugar. As written, these would default to being classified as sweet, which may overstate the case, or fall through unclassified, which understates it. This needs an explicit decision: either treat partial-sugar modifiers the same as no-sugar (exclude), or introduce no new tier and accept the imprecision — but the ticket currently doesn't acknowledge the case exists at all, so it will get decided by accident during implementation rather than on purpose.

Missing: Alias-Overlap Exclusivity Test
The test list proves correct classification behaviors (multilingual matching, no-sugar exclusion, milk tea vs. soda separation) but never proves that the carb alias list and the sweet alias list don't accidentally share an entry that shouldn't be shared. Given both lists are maintained separately and will grow over time, a test that fails if the same raw string appears in both lists unintentionally (as opposed to a food like 珍珠奶茶 that legitimately deserves both flags) would catch a real class of future bugs.

Missing: Explicit Handling of Older Confirmed Snaps Without Sweet Metadata
Backfilling is correctly out of scope, and backward-compatible JSON reading is mentioned — but the ticket doesn't say what the aggregation does with a pre-feature confirmed snap that has no sweet-classification field at all. It should say explicitly: a missing sweet-classification field is treated as unclassified and excluded from sweet counts, not treated as "confirmed not sweet." Otherwise this is left to whoever implements it to guess, and guessing wrong would silently undercount sweet foods for any user with meal history predating this feature, without anyone noticing.
