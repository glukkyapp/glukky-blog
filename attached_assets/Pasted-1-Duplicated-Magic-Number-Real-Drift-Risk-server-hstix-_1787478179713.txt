1. Duplicated Magic Number — Real Drift Risk
server/hstix-correction.ts defines HSTIX_CORRECTION_WINDOW_MS = 5 * 60 * 1000 as the supposed single source of truth. But getLatestCorrectableHstixReading and updateHstixReadingWithinCorrectionWindow in server/storage.ts both hardcode 5 * 60 * 1000 directly instead of importing that constant. Right now they happen to match, but if anyone changes the window to, say, 3 minutes later, they'll edit the helper constant, the UI will show a 3-minute window, but the actual database enforcement in storage.ts will silently keep using the old 5-minute cutoff — a real, silent inconsistency between what the app displays and what it enforces. Fix: import HSTIX_CORRECTION_WINDOW_MS into storage.ts and compute cutoff from it, not from a second hardcoded literal.

2. Scope Conflict With #819's Own Spec
This changelog bundles "Added a permanent, non-paywalled HStix bottom-nav tab" together with the #819 correction-window work. But #819's own spec explicitly listed as out-of-scope: "No new screen, route, bottom-nav item, or navigation flow is introduced." If the bottom-nav tab is actually fulfilling the earlier, separately-agreed "persistent HStix access" feature (from several turns back), that's fine functionally — but reporting it under the same changelog as #819 blurs the boundary and makes it look like #819 violated its own stated scope. Worth a one-line clarification in your tracking: is the bottom-nav tab tracked as a separate task, with #819 strictly being just the correction-window addition on top of it? If so, say so explicitly in the changelog so it doesn't read as scope creep.

3. Client Timer Still Depends on Device Clock
The Home useEffect computes delay = new Date(correctionExpiresAt).getTime() - Date.now(). The value of correctionExpiresAt is correctly server-issued, but the comparison against "now" still uses the device's own clock. If an elderly user's phone clock is off (not uncommon on older/neglected devices), the UI might revert the button early or late relative to the true server-side window. This is bounded and non-critical because the actual PATCH request is still validated server-side regardless of what the client thinks — so worst case is a cosmetic mismatch, not a data-integrity bug. But it should be called out explicitly as an accepted tradeoff, and you should add a test confirming server-side rejection works correctly even when a client's local clock is deliberately skewed, since that's the real safety net doing the work here.

4. Boundary Race Between Auto-Close Timer and In-Flight Submission
The timer that auto-closes the correction sheet fires based on correctionExpiresAt, and if a user taps submit right at, say, 4:59.8 into the window, the PATCH request might still be in flight when the timer fires and forcibly closes the sheet at 5:00.0. When the PATCH response later arrives (success or HSTIX_CORRECTION_EXPIRED), its callback (onDone or onHstixCorrectionExpired) will fire against a sheet that's already closed. React state setters are idempotent so this won't crash, but it could produce a confusing double-toast, or a "correction expired" toast appearing after the user already saw the sheet close silently from the timer. This specific race isn't in your listed test cases — add one: "submit initiated 200ms before expiry, response arrives 200ms after timer-triggered auto-close."

5. Silent Note Truncation
note.trim().slice(0, 500) silently drops anything past 500 characters with zero user feedback. Low priority given this is meant to be a short optional note, but worth either raising the limit or surfacing a truncation warning — currently a user (or a caregiver typing on their behalf) could lose part of what they wrote with no indication anything was cut.

6. Needs Explicit Confirmation: Sample-Size Threshold Ordering
You state "Food-specific HStix cards and lift calculations now only use explicit on_time evidence." Confirm explicitly that the totalMeals >= 25 sample-size gate from earlier is computed after filtering to on_time-only readings, not before — i.e., a food needs 25+ on_time readings, not 25+ readings of any timing tier with only some of them being on_time. If the threshold is checked before filtering, a food could pass the sample-size gate on mostly delayed/unrelated data and then get a misleadingly confident-sounding card built from a much smaller effective on_time sample. This isn't visible in the code shown, so it needs a dedicated test case, not just an assumption.
