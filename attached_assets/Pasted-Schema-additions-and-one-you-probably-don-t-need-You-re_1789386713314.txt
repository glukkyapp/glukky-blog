Schema additions, and one you probably don’t need
You’re missing four things, but only three actually need a persisted column:
•	 piggyBankMode : text/enum,  "garden" | "photo" | null . Needed.
•	 piggyBankPhotoSetIndex : integer, which of the 3-4 sets is next in rotation. Needed.
•	 piggyBankModeAutoAssigned : boolean, was the current cycle’s mode set by fallback rather than a tap. Needed, both for the yusycyn test switch’s correctness and for firing the analytics event exactly once (more below).
•	Earned photo progress: you almost certainly don’t need to store this. Since photos unlock deterministically at every 5 coins,  unlockedPhotoCount = Math.floor(coins / 5)  is derivable from the existing  piggyBankCoins  field at read time, the same way  fillPct  is already derived for the garden. Persisting it separately just creates a second source of truth that can drift out of sync with the coin count.
The race condition the ticket doesn’t spell out
Nothing in what you’ve shown handles what happens if a manual tap and the first-coin auto-assignment land at nearly the same moment.  awardCoins  and a new “set mode from tap” endpoint would both be trying to write  piggyBankMode  at once. The existing codebase already has the right pattern for this,  startNewPiggyBankGarden ‘s conditional  UPDATE ... WHERE gte(coins, 60)  that only succeeds if the precondition still holds. Both the auto-assign path and the manual-choice path need the same treatment:  UPDATE ... SET mode = X WHERE mode IS NULL RETURNING . Whichever write lands first wins; the other becomes a no-op. This matters concretely for analytics correctness: if a user’s tap loses that race, the client must not fire  garden_choice  just because the user tapped it, it should only fire based on what the server actually confirms was set. Otherwise you could log a  photo_choice  event for a cycle where the server’s own record says  piggyBankModeAutoAssigned = true , which is exactly the corrupted-metric scenario flagged earlier in this conversation.
Firing  reward_auto_assigned  without double-counting
Since there’s no server-side PostHog call in this codebase (calls are centralized in the client  posthog.ts  helper per the ticket’s constraint), the client has to infer that an auto-assignment happened by reading  piggyBankModeAutoAssigned  off the poll response, not by the server telling it directly. That means the client needs a de-dupe guard, a ref or local flag, so that repeated polls while  piggyBankModeAutoAssigned  stays true don’t refire the event on every fetch. Fire it once, the first time that flag is observed to flip from false/absent to true for the current cycle, the same pattern you’d use to avoid double-firing  garden_choice  on a re-render.
Rotation only advances on completed photo cycles
 piggyBankPhotoSetIndex  should only increment when the cycle that just completed had  piggyBankMode === "photo" . If a user does garden mode for three cycles in a row and then picks photo, they should land on set 1, not set 4. That means  startNewPiggyBankGarden  (which will need a mode-agnostic rename at this point, it’s no longer garden-specific) needs a conditional: bump the set index only inside the branch where the completing cycle’s mode was photo.
Two things this ticket leaves as open decisions
The  needsRewardSetup / reward  fields are now dead weight. Since  /api/piggybank/reward  already returns 410, nothing writes  piggyBankReward  or reads  piggyBankNeedsRewardSetup  meaningfully anymore,  mode === null  is now the real signal for “needs a choice.” Worth explicitly deciding whether to drop these two fields from the schema and API response in this same task, or leave them as inert legacy columns for now, either is fine, but it should be a decision, not an accident.
The yusycyn-only switch needs server-side email enforcement, not just UI hiding. The ticket says “other users cannot access it,” which means the endpoint itself needs to check  req.user.claims.email === "yusycyn@gmail.com"  (or equivalent) and reject everyone else, and it likely needs to bypass the  WHERE mode IS NULL  guard entirely so QA can force-switch mid-cycle, unlike the real user-facing choice endpoint.
