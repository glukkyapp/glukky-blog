3. The generalized award code preserves the existing race condition
Your code accurately reflects the current pattern, but it still performs:

text

Check cap

Insert event
Increment balance
as separate operations. Two concurrent requests could still both pass the duplicate check and both increment balance.

Since you listed concurrent retries and award-source uniqueness as part of the intended automated checks earlier, this needs an explicit implementation requirement:

text
Create the ledger event and increment the balance atomically.
Enforce uniqueness on the event identity per user at the database layer.
If the event already exists, award zero points.
This does not require a new balance or ledger. It strengthens the existing piggy_bank_events mechanism. The actual migration/constraint syntax must follow the real schema, so it should not be guessed here.

If current records use exactly snap_<meal ID> and hstix_<reading ID>, compatibility wrappers should preserve those exact strings rather than converting them to food_snap_<ID> or hstix_reading_<ID>. Otherwise existing events may no longer be recognised as duplicates.

type PiggyBankAwardInput = {
