Important improvement: ID generation
Your task says:

“IDs are generated by the app and are not derived from mutable labels…”

This is correct in principle, but generateComponentId() needs a concrete rule, otherwise a random ID may be hard to curate and a label-derived ID can become inconsistent.

Recommended implementation:

text
1. Existing catalog match:
   Reuse the existing stable ID.

2. New, sufficiently specific food:
   Generate an opaque immutable ID such as:
   food_<ULID>
   Example: food_01KABC...

3. Store the official English/Chinese/Cantonese labels separately on the catalog entry.

4. Human curation may change labels, aliases, GI mapping, classification,
   verification, or active/retired status — but never changes the ID.
This is stronger than generating udon_noodles from the current English name because it remains stable even if the label later changes from “Udon noodles” to “Udon.”

If you specifically prefer readable IDs such as mai_sin, that is still workable for your pre-seeded, manually reviewed catalog. But for runtime-created entries, opaque generated IDs avoid duplicate or messy slugs. The ID is hidden from users anyway.

One code adjustment: candidate ID handling
In this proposed resolver:

ts
if (candidate.id) {
  const component = await findActiveComponentById(candidate.id);
  if (component) {
    return { kind: "resolved", component };
  }
}
Do not allow Claude to supply a field called simply id, because it looks like an authoritative database identity.

Use:

ts
candidateInternalId?: string | null;
Then use it only as a hint:

ts
if (candidate.candidateInternalId) {
  const component = await findActiveComponentById(
    candidate.candidateInternalId,
  );

  if (
    component &&
    candidateLabelsAreCompatible(component, candidate)
  ) {
    return { kind: "resolved", component };
  }
}
That prevents a model output such as:

json
{ "id": "mai_sin" }
from overriding contradictory labels.

The server still owns the actual FoodComponentReference.id.

Exact matching and automatic creation
The resolver flow is good:

text
1. Check an existing exact stable candidate ID, if valid.
2. Check official labels and aliases through one shared normalization function.
3. If exactly one active catalog match exists, use it.
4. If multiple match, preserve as unresolved.
5. If no match and the component is sufficiently specific, atomically create an active unverified component.
6. If too broad or conflicting, retain as history-only text.
Do not bring back:

Substring matching.

Embedding similarity.

Category-only matching.

Frequency-based identity guessing.

Global popularity tie-breaking.

Atomic creation
This is crucial:

ts
return db.transaction(async tx => {
  // Repeat exact-match lookup inside transaction
  // Insert only when still no entry exists
});
Two users may submit the same newly recognised food at almost the same time. The database needs to prevent two separate rows from being created.

In addition to the application transaction, rely on database uniqueness constraints for normalized official labels and aliases. If an insert conflicts, catch the uniqueness violation, reload the existing matching component, and return that component instead of failing the FoodSnap request.
