Step 6 — Hash Server-Side distinctId in server/posthog.ts
Uses Node's built-in crypto — no extra package needed:

ts
import { createHash } from 'crypto'

// Non-reversible hash of internal DB ID — prevents PostHog receiving raw integer user IDs
// SHA-256 hex, no salt — goal is non-reversibility for a recipient, not password security
function hashId(id: string | number): string {
  return createHash('sha256')
    .update(String(id))
    .digest('hex')
}
This means PostHog receives e.g. "a3f2c1..." instead of "4821". PostHog can still track sessions consistently (same user always hashes to the same value) but cannot reverse the hash to find the DB user ID.

One Known Edge Case to Watch
sanitise() uses lowercase + strip separators matching (glucosemmol matches glucoseMmol, glucose_mmol, GlucoseMmol). This is intentional — it catches camelCase, snake_case, and mixed variants. The one risk is false positives: a legitimate key like mealCount contains meal as a substring.

The current implementation strips exact matches after normalisation, not substring matches — so mealCount → mealcount after normalisation, which does not match the blocked key meal. Safe.

If you ever add a property key that happens to normalise to an exact blocked string, it will be silently dropped. The MCHK comment in both files should make this visible during code review.
