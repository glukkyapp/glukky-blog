Two locale keys are referenced but never defined
The full-photo popup code references t("roadmap.photo_dialog_title") and t("roadmap.photo_expand_aria", ...), but neither key appears in any of the English, Traditional Chinese, or Cantonese translation blocks shown here. If these are genuinely missing (not just omitted from this message for brevity), they'll fall back to raw key names or empty strings, the sr-only dialog title in particular is an accessibility-load-bearing string, so this isn't cosmetic if it's actually absent. Worth a quick check that all three locale files have both keys filled in.

photo_slot_locked looks like a leftover from the grid design that was already removed
"Photo slot {{number}}, locked until {{points}} points" is exactly the kind of accessibility label the old 3×4 grid of individually-locked tiles needed, but that grid was explicitly torn out in the previous ticket in favor of the single full-size display. If nothing in the current single-photo UI actually renders per-slot locked states anymore, this string (and its three-locale translations) is dead code being polished rather than removed. Worth confirming whether something still references it before spending effort wording it correctly, if it's unused, delete it instead.

The mode-aware popup's correctness depends on timing, not just logic
The CoinSavedPopup branches on piggy?.mode, defaulting to Garden wording whenever mode isn't exactly "photo", which includes null. That's fine as long as the client always has the server's freshly-resolved mode (including the outcome of a first-coin auto-assignment) by the time this popup renders. But if the popup is triggered optimistically, right as the coin-award request fires, before the response with the resolved mode comes back, there's a window where a cycle that just got auto-assigned to photo could still read mode: null on the client and incorrectly show "your garden grew." Worth confirming the popup only renders after the award response (with its resolved mode) has actually landed, not on an optimistic pre-response render, since this is exactly the same race-condition class flagged earlier in this build.
