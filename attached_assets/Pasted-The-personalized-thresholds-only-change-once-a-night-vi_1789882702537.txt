The personalized thresholds only change once a night, via the scheduled job — not continuously. Setting  staleTime: 0  means the app will refetch this data every single time either screen mounts or regains focus, even seconds after the last fetch, even though the underlying threshold data realistically only changes once every 24 hours.
For an app built for elderly users, this trades a real correctness edge case (stale thresholds shown for part of a day) for a very frequent one (an extra loading flicker every time someone switches back to the app or reopens the screen). Given the threshold job runs nightly, a modest non-zero  staleTime  — say, 10–15 minutes — would still catch the threshold change well within the same day, while meaningfully cutting down on unnecessary refetch flicker for a screen elderly users may check multiple times a day.
Worth asking: “Given the threshold job only runs nightly, would a staleTime of around 10-15 minutes instead of exactly 0 be sufficient? This still catches a threshold change within the same day, while reducing how often the meal-impact badge briefly reloads every time the app regains focus.”
