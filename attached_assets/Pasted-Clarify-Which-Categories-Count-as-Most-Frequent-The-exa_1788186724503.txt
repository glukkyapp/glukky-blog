Clarify: Should Retained-History Search Stay Mode-Scoped
Your fix correctly identifies that buildGeneralGlucosePatternComponents and buildHstixFoodCards both apply ranking-eligibility filters (minimum meal count, lift/reliability gates) on top of basic validity, which wrongly excludes valid-but-infrequent foods like chicken breast. The fix should remove that eligibility filter for search purposes — but it's ambiguous whether search should still be scoped per mode (General mode searches generalMeals, HStix mode searches hstixSnaps) or become one merged pool across both modes.

I'd recommend keeping it mode-scoped: General mode searches all retained non-deleted meal history (via buildRetainedFoodHistory(generalMeals)), and HStix mode searches only HStix-linked history (buildRetainedFoodHistory(hstixSnaps)), each now skipping the card-eligibility filter within its own source. This preserves the meaning of "HStix recorded food" mode — showing only foods actually tracked with glucose readings — while fixing the General-mode gap that misses chicken breast. Merging both pools into one universal search would blur that distinction and let HStix mode surface foods with no HStix history at all.
